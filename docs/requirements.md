## 1. 项目背景与范围

企业园区每日有外部访客进出，靠纸质登记存在三个问题：预约靠电话、到访无核验、事后无追溯。本系统把「员工提预约 → 审核员审批 → 生成核验码 → 门岗核验入场 → 离场登记」这条链路搬到线上，并在每个节点留下审计与处理记录。

### 1.1 范围内

- 三种角色的登录、鉴权与权限隔离
- 预约单的全生命周期（提交、审核、驳回、取消、核验、入场、离场）
- 状态变更审计、业务操作留痕
- 用户与部门的后台管理
- 三类统计：总览卡片、按日趋势、按部门分布

### 1.2 范围外（不做，别加）

- 访客自助注册、访客端小程序
- 短信/邮件通知、二维码生成（核验码是 6 位数字，手工输入）
- 人脸识别、身份证读卡器对接
- 多租户、多园区
- 复杂审批流引擎（状态机写死，不做可配置流程）

> 明确不做，是为了答辩时能答上"为什么不做"，而不是被问住。

## 2. 角色与权限

### 2.1 三个角色

| 角色码 | 名称 | 定位 |
|---|---|---|
| `EMPLOYEE` | 员工 | 发起预约的人 |
| `AUDITOR` | 审核员 | 审批本部门预约、兼门岗核验 |
| `ADMIN` | 管理员 | 系统管理员，全部权限 |

### 2.2 权限矩阵

| 功能 | EMPLOYEE | AUDITOR | ADMIN |
|---|---|---|---|
| 登录 / 查看本人信息 | ✅ | ✅ | ✅ |
| 新建预约 | ✅ | ❌ | ✅ |
| 查看本人预约 | ✅ | — | — |
| 取消本人预约 | ✅（仅 0/1/2 状态） | ❌ | ✅（任意单） |
| 查看本部门预约 | ❌ | ✅ | ✅ |
| 审核 / 驳回（本部门） | ❌ | ✅ | ✅ |
| 生成核验码（本部门） | ❌ | ✅ | ✅ |
| 门岗核验入场 / 离场 | ❌ | ✅（本部门） | ✅（全部） |
| 查看全部预约 | ❌ | ❌ | ✅ |
| 用户增删改查 | ❌ | ❌ | ✅ |
| 部门增删改查 | ❌ | ❌ | ✅ |
| 统计总览 / 趋势 | ❌ | ✅（本部门口径） | ✅（全局） |
| 按部门统计 | ❌ | ❌ | ✅ |
| 查看审计日志 | ❌ | ✅（本部门单） | ✅（全部） |

### 2.3 权限实现要求

1. **后端是唯一权威**。前端菜单隐藏只是体验，不是安全边界；每个接口必须独立校验角色。
2. `@RequireRole` 注解在拦截器里拦角色；**部门范围在 Service 层二次校验**（`apply.deptId != user.deptId` → 403 `DEPT_SCOPE_DENIED`），因为角色对了不代表数据范围对。
3. 越权访问返回 `403`，不是 `404`，也不是"返回空列表"。返回空列表会让越权看起来像"没数据"，掩盖问题。

## 3. 核心业务对象

| 对象 | 说明 | 关键规则 |
|---|---|---|
| 部门 | 组织单元 | 停用后不能新建预约，历史数据保留 |
| 用户 | 系统账号 | 停用即不能登录；不物理删除 |
| 预约单 | 一次来访申请 | 状态机受控，状态只能由 `transit()` 改 |
| 到访记录 | 一次实际到访 | 一条预约最多一条，入场插入、离场更新 |
| 处理记录 | 每次业务操作 | 只增不改，记录操作人当时的姓名与角色 |
| 状态审计 | 每次状态变更 | 只增不改，`from_status`/`to_status` 必须成对 |

## 4. 预约单状态机

### 4.1 六个状态

| 值 | 名称 | 说明 |
|---|---|---|
| 0 | 待审核 | 员工已提交，等审核 |
| 1 | 审核通过 | 审核员已通过，等排期/生成码 |
| 2 | 待到访 | 核验码已生成，等访客到场 |
| 3 | 已到访 | 门岗已核验入场 |
| 4 | 已离开 | 离场登记完成，终态 |
| 9 | 驳回/取消 | 异常终态 |

### 4.2 允许流转

```
0 待审核 ──approve──→ 1 审核通过 ──verify-code──→ 2 待到访 ──checkin──→ 3 已到访 ──checkout──→ 4 已离开
   │                      │                          │
   └──────reject──────────┴──────cancel──────────────┘
                          ↓
                    9 驳回/取消
```

| from | 允许的 to | 触发动作 |
|---|---|---|
| 0 | 1, 9 | approve / reject、cancel |
| 1 | 2, 9 | verify-code、cancel |
| 2 | 3, 9 | checkin、cancel |
| 3 | 4 | checkout |
| 4 | — | 终态 |
| 9 | — | 终态 |

**不在上表的转移一律 `400 STATE_NOT_ALLOWED`**，包括：反向流转（4→3）、跳级（0→3）、终态复活（9→0）。

### 4.3 状态变更的事务要求（硬性）

每一次状态变更必须在**同一个事务**内完成三件事：

```java
@Transactional
public void transit(Long applyId, int toStatus, String action, Long operatorId, String remark) {
    // 1. 校验当前状态是否允许目标状态，不允许抛 BizException(400, "STATE_NOT_ALLOWED")
    // 2. UPDATE visitor_apply SET status = ? WHERE id = ? AND status = ?   ← 带上旧状态做乐观锁
    // 3. INSERT biz_status_change_log (from_status, to_status, action, operator...)
    // 4. INSERT apply_process_record (action, operator, remark...)
}
```

- 第 2 步的 `AND status = ?` 是防并发关键：两个审核员同时点通过，只有一个能 `UPDATE` 成功（影响行数 1），另一个影响行数 0，直接抛状态错误。
- 任一插入失败，整个事务回滚，**不允许出现"状态变了但没日志"**。
- 全项目唯一允许改 `status` 的地方就是这个方法，代码评审时用 `grep "status ="` 检查有没有绕过。

### 4.4 异常场景（必须处理，答辩会问）

| 场景 | 期望行为 |
|---|---|
| 已离场（4）再次入场 | `400 STATE_NOT_ALLOWED` |
| 同一核验码重复入场 | `409 DUPLICATE_CHECKIN`（唯一键 `uk_record_apply` 兜底） |
| 核验码错误 | `400 VERIFY_CODE_INVALID` |
| 未入场直接离场 | `400 NOT_CHECKED_IN` |
| 审核员审别的部门单 | `403 DEPT_SCOPE_DENIED` |
| 员工取消别人的单 | `403 FORBIDDEN` |
| 员工取消已到访的单 | `400 STATE_NOT_ALLOWED` |
| 两个审核员同时点通过 | 一个成功，一个 `400 STATE_NOT_ALLOWED` |
| 停用用户持旧 token 请求 | `401 USER_DISABLED` |

## 5. 功能需求

### 5.1 通用（FR-01 ~ FR-05）

### 5.3 审核员（FR-20 ~ FR-25）

| 编号 | 需求 |

## 6. 统计指标

| 指标 | 口径 | 来源 |
|---|---|---|
| 今日预约数 | `visitor_apply` 中 `DATE(create_time)=CURDATE()` 的条数 | `/stats/overview` |
| 待审核数 | `status=0` 的条数 | `/stats/overview` |
| 今日到访数 | `visitor_record` 中 `DATE(checkin_time)=CURDATE()` 的条数 | `/stats/overview` |
| 本月到访数 | `visitor_record` 中 `checkin_time` 在本月内的条数 | `/stats/overview` |
| 平均停留时长 | `AVG(TIMESTAMPDIFF(MINUTE, checkin_time, checkout_time))`，只算已离场的 | `/stats/overview` |
| 近 N 天趋势 | 按 `DATE(create_time)` / `DATE(checkin_time)` 分组，缺失日期补 0 | `/stats/trend` |
| 按部门分布 | `visitor_apply` join `sys_department`，`GROUP BY dept_id` | `/stats/department` |

**口径约束**：
- AUDITOR 调用 `/stats/overview` 与 `/stats/trend` 时，所有指标自动加 `dept_id = 本人部门`。
- 空数据返回 0，不返回 `null`——前端图表拿到 `null` 会崩。
- 趋势接口必须返回连续 N 天，缺的在服务端补 0。

## 7. 非功能需求

### 7.1 安全

| 编号 | 要求 |
|---|---|
| NFR-01 | 密码 BCrypt 加密存储，任何响应不得返回 `password` 字段 |
| NFR-02 | JWT 密钥、数据库密码**只从环境变量读**，禁止写在 yaml、代码、README 里 |
| NFR-03 | 令牌过期返回 `401 TOKEN_EXPIRED`，前端清 token 跳登录 |
| NFR-04 | 用户停用后，已签发 token 在拦截器复查 `status` 时失效 |
| NFR-05 | 所有 SQL 走 MyBatis-Plus 参数绑定，禁止字符串拼接 |

### 7.2 审计

| 编号 | 要求 |
|---|---|
| NFR-10 | 每次状态变更写 `biz_status_change_log`，漏写视为 bug |
| NFR-11 | 每次业务操作写 `apply_process_record` |
| NFR-12 | 审计表只增不改不删，无 update/delete 接口 |
| NFR-13 | 记录操作人**当时的姓名与角色**（冗余存储，防改名后追溯不清） |

### 7.3 可用性与部署

| 编号 | 要求 |
|---|---|
| NFR-20 | 提供 `/api/actuator/health`，含 db 检查，供 K8s 探针与 Compose healthcheck 使用 |
| NFR-21 | 无状态服务，JWT 放 header，不依赖 session，可直接水平扩容到 2–4 副本 |
| NFR-22 | 数据库连接池 HikariCP，最大连接 10，避免 4 副本打爆 MySQL |
| NFR-23 | 日志输出到 stdout，由 Docker/K8s 采集，不写文件 |

### 7.4 界面

| 编号 | 要求 |
|---|---|
| NFR-30 | 至少 9 个页面、5 个复用组件 |
| NFR-31 | 状态用彩色标签展示，`StatusTag` 组件统一处理 0/1/2/3/4/9 |
| NFR-32 | 无权限的菜单项不显示；直接输 URL 访问由路由守卫拦截 |
